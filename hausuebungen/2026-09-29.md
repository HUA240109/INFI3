## 1. Vorhersage (vor dem Ausführen notiert)

**Query 1 — `topKuenstler()`** (`song.groupBy` über `kuenstlerId`, `_count._all`, absteigend, `take: 5`):

| Künstler | erwartete Tracks | Begründung |
|---|---|---|
| Nova | 3 | Nordlicht (245 s), Glut (210 s), Funkeln (198 s) |
| Pixel | 2 | Pixelstaub (305 s), Raster (233 s) |
| Solveig | 1 | Fjord (260 s) |
| Ohne Label | 1 | Kurz (120 s) |

Alle vier Künstler, **keine Ausreißer-Gruppierung**: `groupBy` läuft über `Song.kuenstlerId`, also
über die 7 Songs. Ein Künstler ohne Songs (hier keiner) erschiene gar nicht — `groupBy` zählt nur
Gruppen mit mindestens einer Zeile. Reihenfolge bei den Einsern (Solveig/Ohne Label) war von mir als
Tie-Break offen erwartet, deshalb vorsichtig: Prisma/SQLite sortiert Gleichstände nicht garantiert.

**Warum `COUNT(*)` = 4, `COUNT(labelId)` = 3?**

`COUNT(*)` zählt **Zeilen**, nicht Werte — jede Zeile zählt genau einmal, auch wenn die Spalte `NULL`
ist. Die Tabelle `Kuenstler` enthält 4 Zeilen (Nova, Pixel, Solveig, „Ohne Label"), also `COUNT(*) = 4`.

`COUNT(labelId)` zählt nur Zeilen, in denen `labelId` **nicht NULL** ist. Das Schema definiert
`labelId Int?` (optional, `Label?`-Relation), damit ein Künstler ohne Label darstellbar ist — der
Seed legt „Ohne Label" bewusst mit `labelId: null` an. Diese eine Zeile fällt bei `COUNT(labelId)`
weg → 3.

Kurz: `COUNT(*)` ist „Zeilen vorhanden", `COUNT(spalte)` ist „Spalte hat einen Wert".
In Prisma: `prisma.kuenstler.count()` bzw. `count({ where: { labelId: { not: null } } })`.

## 3. Erweiterung: Model `Playlist` (N:M zu `Song`)

### 3.1 Schema (`prisma/schema.prisma`)

```prisma
model Song {
  id          Int       @id @default(autoincrement())
  titel       String
  dauerSek    Int
  kuenstlerId Int
  kuenstler   Kuenstler @relation(fields: [kuenstlerId], references: [id])
  playlists   Playlist[]
}

// N:M zu Song — implizite Join-Tabelle `_PlaylistToSong`.
model Playlist {
  id     Int    @id @default(autoincrement())
  name   String @unique
  songs  Song[]
}
```

Das `playlists Song[]` / `songs Song[]`-Paar genügt; Prisma legt die Join-Tabelle
`_PlaylistToSong` selbst an — kein Zwischen-Model nötig (anders als bei 1:1 mit eigenem Feld).

### 3.2 Migration

```bash
npm run db:migrate -- --name playlist_nm
# └─ 20261005184507_playlist_nm/migration.sql
```

Hinweis: `prisma migrate dev` **ohne** `--name` fragt interaktiv nach dem Migrationsnamen und
hängt in nicht-interaktiven Shells — deshalb `--name` mitgeben.
Danach war ein explizites `npm run db:generate` nötig, sonst kannte der Client `prisma.playlist`
noch nicht (`prisma.playlist` war `undefined`). Das ist bei Prisma 7 relevant, weil der
`postinstall`-Generate-Lauf vor der Schemaänderung passiert war.

Erzeugtes SQL:

```sql
CREATE TABLE "Playlist" (
    "id"   INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "name" TEXT    NOT NULL
);
CREATE UNIQUE INDEX "Playlist_name_key" ON "Playlist"("name");
CREATE TABLE "_PlaylistToSong" (
    "A" INTEGER NOT NULL,
    "B" INTEGER NOT NULL,
    CONSTRAINT "_PlaylistToSong_A_fkey" FOREIGN KEY ("A") REFERENCES "Playlist" ("id") ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT "_PlaylistToSong_B_fkey" FOREIGN KEY ("B") REFERENCES "Song" ("id") ON DELETE CASCADE ON UPDATE CASCADE
);
CREATE UNIQUE INDEX "Playlist_name_key" ON "Playlist"("name");
CREATE UNIQUE INDEX "_PlaylistToSong_AB_unique" ON "_PlaylistToSong"("A", "B");
CREATE INDEX "_PlaylistToSong_B_index" ON "_PlaylistToSong"("B");
```

### 3.3 Die Query: Songs pro Playlist (`src/queries.js`)

```js
// 6. Songs pro Playlist (N:M über die implizite Join-Tabelle).
//    `_count: { select: { songs: true } }` liefert die Zahl direkt am Datensatz —
//    kein JOIN/GROUP BY nötig, auch leere Playlists erscheinen mit 0.
export async function songsProPlaylist() {
  const playlists = await prisma.playlist.findMany({
    select: { name: true, _count: { select: { songs: true } } },
    orderBy: { name: "asc" },
  });
  return playlists.map((p) => ({ name: p.name, anzahl: p._count.songs }));
}
```

Häquivalent in SQL:

```sql
SELECT p.name, COUNT(s.id) AS anzahl
FROM Playlist p
LEFT JOIN _PlaylistToSong pt ON pt."A" = p.id
LEFT JOIN Song s ON s.id = pt."B"
GROUP BY p.id, p.name
ORDER BY p.name;
```

Zwei Punkte, die die `LEFT JOIN`-Variante in SQL betreffen und Prisma automatisch richtig macht:
`_count` nutzt korrekt `COUNT(s.id)` (nicht `COUNT(*)`), sonst wäre die leere Playlist fälschlich 1;
und `findMany` startet von `Playlist`, nicht von `Song` — dadurch tauchen Playlists ohne Songs
überhaupt erst auf (`{ name: 'Noch leer', anzahl: 0 }`). In Prisma ist beides Default.

### 3.4 Seed-Ergänzung (`src/seed.js`)

```js
// Playlists zuletzt: Join-Tabelle braucht existierende Songs.
await prisma.playlist.deleteMany();

const alleSongs = await prisma.song.findMany({ select: { id: true } });
const ids = alleSongs.map((s) => s.id);

await prisma.playlist.create({
  data: {
    name: "Dauerläufer",
    songs: { connect: [{ id: ids[0] }, { id: ids[1] }, { id: ids[2] }] },
  },
});
await prisma.playlist.create({
  data: { name: "Kurz und gut", songs: { connect: [{ id: ids[6] }] } },
});
await prisma.playlist.create({ data: { name: "Noch leer" } });
```

Zwei Dinge, die mich hier gekostet haben: `createMany` kann **keine** Relationen anlegen
(`Unknown argument 'songs'`) — Relationen brauchen einzelne `create` mit `connect`; und
`playlist.deleteMany()` muss **vor** `song.deleteMany()` stehen, sonst blockiert der
FK-Cascade bzw. schlägt der Delete fehl. `createMany` ist beim Löschen übrigens weiterhin der
schnellere Weg — es kennt nur keine `connect`.

## 4. Reflexion

Prisma war dort am kürzesten, wo die Abfrage eine reine Aggregation über eine Relation ist:
`topKuenstler` und die Playlist-Zählung sind je ein `groupBy`/`findMany` mit `_count`, während
SQL dafür jeweils `JOIN` + `GROUP BY` + `HAVING` plus einen zweiten Lauf braucht, um die Namen
nachzuladen (im Prisma-Code sichtbar: `findMany` mit `where: { id: { in: [...] } }`, um das
N+1-Muster zu vermeiden). Besonders `_count` rettet die Semantik — die leere Playlist erscheint
mit 0, ohne dass ich wie im SQL explizit `LEFT JOIN` schreiben und `COUNT(spalte)` statt
`COUNT(*)` setzen muss. Umgekehrt hat Prisma Grenzen, die mich zu `$queryRaw` gezwungen haben:
Query 2 (Künstlerpaare desselben Labels) braucht einen Self-JOIN mit `x.id < y.id` auf dieselbe
Tabelle, und dafür gibt es in der Prisma-API keinen Ausdruck — kein Modell kann sich zweimal
referenzieren. `$queryRaw` ist aber nicht die Schreibweise der Wahl, sondern ein Werkzeug, das man
zielsüchtig einsetzt; bei `_count`- und `groupBy`-Fragen wäre es Dummheit, rohes SQL zu
schreiben, nur weil man es kann. Die zweite Grenze war `createMany` ohne Relationen (siehe 3.4) —
da half kein `$queryRaw`, sondern schlicht `createMany` → `create` mit `connect`. Was den
Prisma-7-Wechsel außerdem teuer macht, sind die Treiber: der `PrismaBetterSqlite3`-Adapter,
`.env`, `prisma7.config.ts` und das explizite `prisma generate` nach Schemaänderungen sind
Rituale, die es beim reinen SQL-Denormalisieren nicht gab; dafür sind Schema, Migration und
Client garantiert konsistent und die Queries typisiert. Ich bleibe für diese Werkzeugkette bei
Prisma, weil die Aggregationen und die N:M-Zählung tatsächlich kürzer sind und die typsicheren
Ergebnisse Fehler beim Zugriff auf Felder früh sichtbar machen — aber ich behalte SQL im Repertoire:
für Self-JOINs, `HAVING`-Kombinationen, die Prisma nicht ausdrücken kann, und für Abfragen, die
über reine CRUD-Muster hinausgehen, greife ich ohne Zögern zu `$queryRaw` oder zur Deno-SQLite.
Kurz: Prisma als komfortable Standard-Abstraktion, SQL als Ausweg, den man kennen und nicht
vermeiden muss.
